# Device history and observed references

Ayan workstream, November 8, 2026. This slice adds private website history and bounded on-box persistence. It does not change fixed detection thresholds, canonical ingestion, mesh frames, or upload/retry contracts. No synthetic observations were written to production. Firmware compilation and host tests are separate from physical board verification.

## Website integration

- Customer: `GET /api/customer/history?id=<customerLinkId>&days=365`. Use the ID from the customer device list, with the current customer cookie. The endpoint rechecks the account/session and the active link belonging to that customer. Other owners and inactive/exercise links return 404.
- Operator: `GET /api/ops/device-history?id=<deviceObjectId>&days=365`. Uses existing operator authentication; demo sessions return 403.
- `days` is an integer 1–365, default 365. It counts UTC calendar days including today. Invalid values return 400, missing authentication 401, nonexistent/exercise devices 404, non-GET methods 405, service failure 503. Responses have `Cache-Control: no-store`.
- Success shape: `{days,daily:[{day,metrics:{sensor:{mean,min,max,count,unit,label}}}],baseline:{status,note,metrics:{sensor:{mean,min,max,count,unit,label,firstObservedAt,lastObservedAt,status}}}}`. Dates are ISO UTC. Baseline metrics may be absent; each available metric has its own status.
- No device ID, home ID, coordinates, address, customer identity, secrets or arbitrary database fields are returned. Daily rows are ascending. Omitted dates are gaps, not zero measurements. Omitted sensors mean unmeasured; do not draw a continuous line across gaps or show missing conditions as safe.
- Overall baseline status is `observed_reference` if at least one metric qualifies; otherwise `insufficient_history`. Use each metric's own status when rendering it. Insufficient metrics still expose their actual count and mean with the insufficient label. Fixed alarms always apply regardless of these averages.

### Existing archive and scheduler

The existing `refreshData` hourly daily-statistics job calls `materializeDailyStats`, which now delegates to the history materializer. No second cloud archive or scheduler is created. `device_daily_stats` keeps its existing unique device/day index and 365-day expiry. `metrics` remains the existing daily-summary field; `qualifiedMetrics` and `qualificationVersion:1` are additive. Existing rows without qualified summaries remain readable but cannot qualify as a baseline.

Recomputation reads canonical `telemetry` only, streams grouped daily results, and replaces recent daily summaries rather than incrementing them. It deduplicates stable event IDs per device; documents without event IDs fall back to their own document ID. Replaying the job does not count observations again. Late observations update their original UTC day.

The window starts at the first full UTC day inside the raw 30-day retention window. The partially expired boundary day and older archived rows are deliberately preserved: recomputing them from surviving raw samples would shrink history. Consequently a late arrival on that oldest partial day is not incorporated. Raw-expired days without existing archives cannot be reconstructed. No backfill from ingestion receipts or legacy readings is attempted. The job must actually run before observations appear here; updates follow the existing hourly cadence, not every UI poll.

### Qualification

Baseline learning currently supports canonical `temperature_c` and `humidity_pct`. A sample must have device-declared observation time (`clockSource: device`), explicit `water_detected:false`, explicit `main_power_available:true`, and reported battery 20–100%. Reported temperature must be below the existing 55 °C hazard threshold and within canonical range. Each reference metric must actually be numeric and within canonical range. Missing safety prerequisites and server-fallback timestamps do not qualify.

A current unresolved critical incident associated with the device **or its home** excludes reference learning. Reads also suppress all baseline metrics while such an incident exists, including previously archived references. Resolution permits recomputation while raw data remains. Historical qualification is the state observed during the last recomputation; this is not a historical incident-interval reconstruction. Changes after raw expiry cannot reclassify the original samples. Observation time is a device assertion, not independently verified hardware time; the existing unknown-time uplink gap below must be fixed before calling this trusted physical provenance.

Each metric needs at least 30 qualifying samples spanning at least 48 hours. These are count-weighted sample statistics, not duration-weighted uptime, calibration, climate normals, occupancy, or safety decisions. Exercise and simulation devices and marked synthetic telemetry are excluded. Sensor reporting frequency can bias averages.

Current actual sketches do not measure temperature/humidity. Box A reports canonical water/mains and Box B reports canonical mains/estimated battery through the existing adapter; their additional raw sensor readings use the legacy endpoint. Those legacy raw readings are not added to this canonical cloud daily archive. A real current box will therefore normally have no temperature/humidity baseline. Do not add sample values for a demo to production.

## Concrete local recorder

Both actual sketches call `local_history::observe(m, own)` from their existing observation callback. Only the box's own messages influence its recorder; relayed neighbors are ignored. Recording does not require Wi-Fi, Internet, cloud acknowledgements, or an SD card. Common headers are copied into Box A, Box B and mesh_test, consistent with the existing firmware sync process. mesh_test receives the headers but does not activate them.

- A fixed ring stores **64 raw reading snapshots**, sampled at most once per five minutes, plus the first reading of a new boot. Continuous operation retains about **5 hours 20 minutes**; gaps and frequent reboots change coverage. This is not every sensor poll, every reading, or an event archive.
- Snapshots retain original boot, sequence, flags, uptime at recording, raw ADC water/flame, acceleration deviation in **mg**, battery in **mV**, sound-hit count and observation epoch. Invalid/unknown time remains epoch zero with F_TIME_VALID clear. It is never filled with reconnect time. Read raw fields only when their validity flags say they were measured.
- Qualified per-metric integer sum/count/min/max and first/last observation times survive ring overwrite and checkpoints across reboot. The mean is derived from sum/count. Counters saturate; a metric stops accumulating at UINT32_MAX samples and serial output labels `aggregate_full`. There is no unbounded sample list.
- NVS namespace `hb_history` has two alternating versioned/checksummed slots. The latest valid slot restores at boot; a corrupt latest slot falls back to the previous valid slot. Failed/unknown versions are not treated as valid history. Checkpoints occur no more often than every 15 minutes per running boot; initialization/first data may checkpoint immediately. This is roughly 96 writes per continuous day, plus restarts, not a flash endurance guarantee. Each write saves the bounded snapshot, not an ever-growing file. `history` prints bytes per slot.
- Up to 15 minutes since the last successful checkpoint can be lost on sudden power loss; scheduler delays and storage failure can extend that gap. Wi-Fi loss alone does not erase the recorder. Both slots share the board's finite NVS partition with existing settings; insufficient storage reports failures and retains only current RAM changes. Physical partition space, flash wear and power-cut atomicity require bench verification.
- Overflow overwrites the oldest raw snapshot and increments a visible counter. Serial `history` shows retained/capacity, overwritten, decimated, duplicate and unknown-time counts, storage availability, unsaved state and write failures. It then prints each reference metric and retained raw snapshots without credentials.

Local qualification requires valid time, known mains present, all expected configured/boot-detected hazard sensors valid, no water/flame/tilt flag, acceleration below the unchanged shake threshold, and sound below the unchanged sound threshold. Box B also requires its configured battery reading at 6600–12000 mV. Box A has no battery ADC and cannot claim battery qualification; its references are conditional only on its installed measured sensors. Box B has no water sensor and cannot establish dry conditions. Local references are therefore a separate, less complete measurement context from the cloud's canonical qualification.

Known water/flame/tilt/shaking/alarm/power-loss/help events impose a 15-minute local learning holdoff, including an initial holdoff following reboot after a retained alert. This is not cloud incident resolution or a certified latch. Unknown clock and backward-moving observation times are excluded from learning but retained as raw evidence. Failed MPU bus reads now omit acceleration validity instead of reporting a false measured zero. Detected/undetected wiring beyond the firmware validity flags remains unverified. No local aggregate modifies alarm thresholds or suppresses an alert.

## Bounded box-to-website replay

`firmware/common/history_sync.h` is included after uplink and local history in both sketches. Each loop calls the independent history transport after the existing uplink loop. It sends the box's own retained raw records directly to the parent's dedicated `POST /api/device/history-sync`, with the existing own `X-Device-Key` and the pinned root CA over verified HTTPS. It does not send these records through canonical or generic ingest, change live alarms, forward neighbors, or depend on the finite mesh/uplink queues. The existing endpoint authenticates device identity from that key and deduplicates stable device/boot/sequence records.

Every attempt is at least 30 seconds apart. Each batch contains the oldest 1–8 retained samples after the RAM acknowledgement cursor, in ascending boot/sequence order. The serialized batch is frozen across timeout, HTTP 503 and incomplete/malformed acknowledgement retries, even if the ring subsequently overwrites its original slots. The firmware advances its cursor only after HTTP 200 and a bounded JSON response with version 1, matching stored count, and every sent exact `boot:seq` ID once. It ignores acknowledgement order but rejects missing, duplicate or unexpected IDs. A reboot clears the cursor and safely replays the retained ring through the endpoint's idempotent records.

The request is `{version:1,snapshot:{boot,seq},samples:[{boot,seq,epoch,uptimeMs,flags,waterRaw,flameRaw,accelMilliG,batteryMv,soundHits}],metrics:{...},overwritten}`. Only nonempty learned metrics with known valid first/last observation times are included, using `{count,sum,min,max,firstEpoch,lastEpoch}` under `water_raw`, `flame_raw`, `accel_dev_mg` or `battery_mv`. The aggregate snapshot identity is frozen from the recorder’s latest observed boot/sequence, independently of each raw chunk. It is at least as new as every sample in that batch; unchanged recorder state produces the same snapshot across chunks, and retry bodies preserve it exactly. Original sample epochs and flags are never altered. Unknown time remains epoch 0 with time-valid clear, including after reconnection. The request body is capped at 4096 bytes; responses, including chunked bodies, are capped at 2048 bytes with nesting limited to four. Connect/read timeouts are five seconds each. This is synchronous firmware HTTP and can delay sampling while a connection attempt runs; timing under real networking load remains unverified.

HTTP 409 pauses synchronization for review and retains the pending batch without advancing the cursor. Other explicit request/auth/configuration rejections (400/401/403/404/413/422) also pause; no permanent-error path silently drops a retained sample. Review the conflict/provisioning first; reboot restarts attempts from retained history. Other transient/network errors retry the same batch. Serial `history` additionally prints sync cursor, pending count, acknowledged count, failure count and paused state without keys or payloads. No requests are sent after all retained samples are acknowledged until a new sample appears.

The parent's website response adds `local:{samples,metrics,overwritten,updatedAt,note}` beside canonical `daily` and `baseline`. The raw local record and device-reported metrics are separate from canonical baseline qualification. Unknown-time rows stay undated and must not be plotted at receipt time. The API/UI backend integration is parent-owned; this helper implements its agreed transport contract.

### Remaining finite-history limits

This is a 64-sample recorder, not an unlimited durable upload journal. Long outages can overwrite unsent samples before a batch is frozen; the cumulative `overwritten` value reports raw ring overwrites, not an exact count of lost cloud uploads. An unacknowledged frozen RAM batch can survive ring overwrite while powered but is lost on reboot if its records have also left the durable ring. Up to the existing checkpoint interval can be lost on power failure. Only five-minute sampled readings are replayed; no full-rate/event/photo archive is added. After reconnecting, eight batches cover a full ring in roughly four minutes plus request durations and newly arriving samples.

The NVS recorder is explicitly bound to the provisioned device ObjectId before restoration or synchronization. Matching identity restores valid slots, including after device-key rotation. Legacy unbound history or a changed device ID causes both old slots to be deleted and verified absent **before** committing the new binding; the recorder starts fresh and never uploads old-home samples. Invalid IDs, failed deletion, failed identity persistence or unavailable NVS disable restore/sync rather than mixing identities. Runtime reconfiguration is not supported. On upgrading from the unbound core implementation, old local samples are intentionally discarded for this privacy boundary; existing cloud records are unchanged. A persistent acknowledgement journal remains a possible durability improvement.

The legacy uplink's separate unknown-time substitution fix belongs to the parent; this helper never calls its telemetry conversion path. Existing Box B RAM uploads (40 requests), mesh pending messages (48), Box A SD logs, and their delivery limitations remain distinct from this direct history sync. An ESP-NOW ACK still means gateway-queued, not confirmed cloud ingestion. No physical reconnection/website delivery claim is made until bench-tested.

## Validation and follow-up

Host C++ tests exercise bounded overwrite, mean/min/max, saturation, duplicates, decimation, absent validity, hazards, unknown/backward time, outage without network calls, restored state, NVS checkpoint frequency/failure and corrupt-slot fallback. Disposable MongoDB tests exercise owner isolation, session revocation, ops/demo authorization, data minimization, qualification/count/span, critical incident blocking, simulation exclusions, retained history after raw deletion and idempotent/late recomputation. Additional host tests exercise identity-preserving restores, changed-ID/unbound-slot resets, failed binding/deletion fail-closed behavior, exact JSON fields and snapshot identity, unknown-time preservation, oldest-first batches, frozen retries during overwrite, all-ID acknowledgement checks, response bounds, own-key verified-HTTPS setup, 30-second pacing and conflict pause. These transport tests need ArduinoJson headers from the local firmware toolchain and explicitly skip if those headers are absent. See the task report for exact commands and final results.

No board was available. Required physical checks: record while disconnected, run serial `history`, reboot after a successful checkpoint, confirm preserved boot/sequence/time and counts, cut power between checkpoints, fill the ring, simulate NVS write failure, and compare actual reconnect delivery against the website's original-time days. Device-side reference data is now sent by the separate history-sync helper when retained samples are pending; physical delivery and website display require bench verification.
